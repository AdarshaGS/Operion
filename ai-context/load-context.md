## What this is

A multi-tenant School ERP SaaS for schools in India. Not a one-off app for a single school — a commercial product, priced per-student/year (₹100–200/student/year range, not finalized). Target: schools with ~500–2,000+ students.

## Vision

One connected system for administration, academics, students, parents, teachers, finance, transport, communication, attendance, and exams — replacing Excel sheets and WhatsApp-based coordination.

Must be: multi-tenant, modular, secure, scalable, auditable, API-first, mobile-friendly, configurable, multi-campus capable.

## Core principle: don't over-engineer

Build module by module. For every feature answer: what problem does it solve, who uses it, what data does it own, what depends on it, is it MVP-required, what's the simplest architecture that supports future growth.

Simple now → extensible later. Not: complex architecture from day one.

## Core architectural concept: Organisation

`Organisation` is the root tenant. Nearly everything (campuses, academic years, users, students, parents, teachers, staff, classes, fees, transport, etc.) is scoped to an organisation.

## Multi-tenancy

Shared database/shared schema with `organisation_id`-based tenant isolation (default choice — don't switch to database-per-tenant without a strong reason). Data across organisations must never leak. Every tenant-scoped table needs a clear boundary; auth/authz/audit must be tenant-aware.

**Implemented**: Hibernate `@TenantId` on a `TenantScopedEntity` base class + a `CurrentTenantIdentifierResolver` reading `TenantContext` (a `ThreadLocal`), verified end to end by `OrganisationTenantIsolationTest`. **Load-bearing gotcha, confirmed by three real bugs now**: the tenant identifier resolves once per Hibernate session/transaction, not per query. `TenantContext.set(...)` must happen *before* the transaction/session that will touch a tenant-scoped entity opens — setting it mid-transaction (e.g. after the first repository call already opened one) silently does nothing. Bit org provisioning (fixed by not wrapping it in one `@Transactional`), login's own membership check (fixed by setting `TenantContext` right after the org is resolved, before querying `OrganisationMembership`), and — a third time, in the SaaS/billing pass — `BillingService.generateInvoice`, which needs to count a *specific* org's students from a platform-admin request that otherwise carries no org in `TenantContext` at all; fixed the same way as org provisioning, by not wrapping the method in `@Transactional` so each call gets its own fresh session.

## Identity model

- `User` = authentication identity, separate from `Person`.
- A person can be student, parent, teacher, staff, admin — and can hold multiple relationships at once (e.g. one person can be a parent of multiple students AND a staff member).
- Don't assume a 1:1 person↔user mapping.

## RBAC

`User → Organisation Membership → Role → Permissions`. Roles should be configurable, not hardcoded. Permissions granular (e.g. `STUDENT_VIEW`, `FEE_COLLECT`, `ATTENDANCE_MARK`) but not overbuilt.

**Implemented so far**: the data model, plus login and tenant-context wiring only — no permission-level enforcement yet. Auth is JWT (stateless, chosen over server-side sessions to suit the planned SPA + React Native app), issued by `POST /api/v1/auth/login` scoped to one org at a time (slug + email + password → a token embedding both ids, not a separate post-login org-switcher). Password hashing via `spring-security-crypto` (BCrypt) only — deliberately not the full `spring-boot-starter-security`, to avoid its opinionated default filter chain. JWT library is JJWT with the **gson** backend, not jackson (this project runs Jackson 3.x under the `tools.jackson` package per Spring Boot 4.1's rebrand; jjwt-jackson would clash with it). Provisioning an org also creates its first admin login (User + Person + OrganisationMembership on the Org Admin role) — the seeded role needs someone assigned to it. **Next Foundation loose end**: nothing currently checks a caller's actual permissions, only that their token is valid.

## Academic structure

`Organisation → Academic Year → Grade/Class → Section → Student`. Student's identity ≠ their academic enrollment — enrollment is modeled separately per academic year so history survives promotions/transfers. Never just put a `class_id` column on the student.

## Parent/Guardian model

Many-to-many with students (a parent can have multiple children; a student can have more than 2 guardians). Relationship carries attributes: relationship type, is primary guardian, is emergency contact, can pickup, can receive communication, contact priority.

## Student lifecycle

Admission → Enrollment → Academic Year → Class/Section → Attendance → Exams → Fees → Promotion → Transfer → Graduation. Historical records must be preserved, not overwritten.

## Tech direction

Modular monolith (not microservices) in Java/Spring Boot, MySQL, Redis (only when there's a real use case), Docker, REST APIs, Gradle. Don't add Kafka/event streaming prematurely.

Running Spring Boot 4.1 / Hibernate 7.4 (newer than what most docs/training data assume) — it split several autoconfiguration classes into their own per-feature modules that aren't pulled in by the underlying library alone: `spring-boot-hibernate` (`HibernatePropertiesCustomizer`), `spring-boot-data-jpa-test` (`@DataJpaTest`), `spring-boot-flyway` (Flyway autoconfiguration — just having `flyway-core`/`flyway-mysql` on the classpath is *not* enough). If a Spring Boot class "should" be on the classpath but isn't found, check for a newly-split module first before assuming it's misconfigured.

**`@DataJpaTest` gotcha**: the slice has no Jackson `ObjectMapper` bean. A service that (transitively) depends on `AuditLogService` — every module that writes to the shared audit ledger, which by design is most of them — can't be pulled into a test via `@Import(SomeService.class)` if that chain reaches `AuditLogService`. Worse, `@Import`-ing a plain test-local `@Configuration` class (e.g. just to supply an `ObjectMapper` bean) breaks `@EnableAutoConfiguration` base-package detection in this slice with an opaque `Unable to retrieve @EnableAutoConfiguration base packages` failure. The fix used in the Attendance module's tests: construct the service under test by hand (`new AttendanceService(...repos..., new AuditLogService(auditLogRepository, new ObjectMapper()))`) instead of `@Import`-ing it — `AuditLogRepository` itself is fine to `@Autowired` since it's picked up by the slice's normal repository scan. Expect to hit this again in Fees (payments/refunds are audit-heavy by design).

## Database principles

Normalized, explicit FKs, unique constraints, indexes where queries need them, audit fields (`id`, `organisation_id`, `created_at`, `updated_at`, `created_by`, `updated_by`, `status`) — but only where they make sense, not blindly on every table. Soft-delete only where justified. Preserve history where the business needs it.

## API principles

RESTful, versioned (`/api/v1/...`), consistent, validated, authenticated, authorized. Don't design APIs before the domain model is settled.

## Auditability

Track who changed what, when, for which organisation — for meaningful business events (student created/transferred, fee collected/refunded, attendance/marks modified, permissions changed).

## Security

Non-negotiable from day one: auth, authz, tenant isolation, password/session/token security, API security, input validation, SQL-injection/CSRF protection, sensitive data protection, secure config.

## SaaS/billing

`Organisation → Subscription → Plan → Usage → Billing` is a future layer. Keep billing decoupled from module logic now — don't build billing before the core product works.

**Now partially built** (backend only, once the core product's ten modules were done) — see `## SaaS/Billing (Option B) — a separate platform-admin plane` further down for the actual implementation.

## How to work with me (the user)

- Work incrementally, one module at a time — never generate the whole app.
- When asked to build a module, first cover: business purpose, actors, responsibilities, entity model, relationships, DB schema, constraints, APIs, security considerations, implementation plan, test cases — then wait for a decision before moving on.
- For every entity: ownership, scope (org/campus/academic-year/global), lifecycle, relationships, whether history must be preserved, uniqueness, indexing, authorization, audit needs.
- When multiple valid approaches exist, lay out Option A vs Option B with a recommendation and reason. Priority order: correctness, simplicity, maintainability, security, scalability, performance. Don't optimize for scale the product doesn't have yet.
- GitHub issues follow EPIC → Feature → Sub-feature → Technical task. Meaningful units of work, not hundreds of tiny issues.
- A module is "done" only with: domain model, DB schema, relationships, validation, business rules, authorization, APIs, error handling, audit coverage, tests, migrations, docs, seed data where needed.

## Avoid

Building everything at once; unneeded microservices; generic catch-all tables; overusing JSON columns; hardcoding school-specific workflows or a single academic year; assuming uniform school structure or exactly-two-parents; storing current class directly on student when history matters; mixing auth identity with business entities; fat controllers/services; adding Redis/Kafka without a real need; billing before the core product; dashboards before transactional workflows are stable.

## React admin portal (`web/`)

Started per erp-system-plan.md §4, with three decisions confirmed up front: lives in this repo under `web/` (not a separate repo), **MUI** as the component library (Ant Design was the alternative, left open by the plan), and the first working slice is an auth shell plus one full CRUD module end-to-end (Students) as the template every later module follows — not just a login screen.

**Stack**: Vite + React + TypeScript, MUI (`@mui/material` v9), React Router v7. `src/api/` is a hand-written typed client (`client.ts` wraps `fetch`, injects the `Authorization: Bearer` header from `tokenStore.ts`'s localStorage-backed session, throws a typed `ApiError` on non-2xx using the backend's `{error: string}` shape, and now has all four verbs — `get`/`post`/`patch`/`put`, `put` added for Communication's preference-setting endpoint) — no OpenAPI/codegen exists yet since the backend has no springdoc dependency; DTOs are hand-typed per module and will drift if the Java DTOs change without a matching frontend update (money fields are typed `number`, matching how Jackson serializes `BigDecimal` as a JSON numeric token, not a string). `src/auth/` (`AuthContext`, `LoginPage`, `ProtectedRoute`) and `src/layout/AppLayout.tsx` (AppBar + permanent Drawer) are the reusable shell. **Backend additions this required** (discovered by actually trying to wire a screen to the real API, not designed up front — same pattern each module has followed, **except Fees, Transport, Library, and Inventory**, whose backend API surfaces were already complete with nothing to add):
- `LeaveRequestController.list()` (`com.operion.hr.api`) required both `staffProfileId` and `status` as query params — there was no way to build an org-wide "pending approvals" inbox (every prior module's core-flow page had a natural pending-items list surfaced directly by the backend; HR's didn't). Made both params optional: `staffProfileId` alone lists one employee's full history, `status` alone (no `staffProfileId`) is the org-wide inbox, both together scope to one employee's history by status — same shape decision as Communication's optional `status` param on `AnnouncementController.feed()`. Added `LeaveRequestRepository.findByStaffProfileId`/`findByStatus` to back it; no dedicated service change needed, the branching lives in the controller like every other simple-CRUD list endpoint in this codebase.
- Closing the "Academics itself is list+create only" gap flagged repeatedly earlier in this doc: this was a genuine **backend** gap, not just an unwired frontend — `GradeLevel`/`Subject`/`SchoolClass`/`Section`/`ClassSubject` all had a `status` field and an `INACTIVE` enum value with **zero code path that ever set it** (no setter, no service method, no endpoint). Added a `changeStatus(...)` method to each of the five entities, a matching `AcademicService.change*Status(...)` method for each, and a `POST /{id}/status` endpoint on each of the five controllers, all sharing one new `ChangeStatusRequest(String status)` DTO (same "one shared shape, each entity parses its own enum" reasoning as `HR`'s `ChangeStaffStatusRequest`) — no guard logic needed since these are plain two-value `ACTIVE`/`INACTIVE` toggles, unlike `LeaveRequest`'s one-way `PENDING→APPROVED|REJECTED|CANCELLED` machine. Also found `TeacherAssignment.end(LocalDate)` already existed as a business method on the entity with **no controller endpoint exposing it** — the only way to end an assignment was the side-effecting reassignment path inside `AcademicService.assignTeacher()`. Added `POST /api/v1/teacher-assignments/{id}/end` (`EndTeacherAssignmentRequest(LocalDate endDate)`) so the frontend can end an assignment explicitly (e.g. a teacher leaving) without needing to reassign to someone else first.
- `PersonController` (`com.operion.identity.api`, `POST/GET /api/v1/persons`, `GET /api/v1/persons/{id}`) — Student creation needs a `personId` and no endpoint existed to create one.
- `CampusController` and `AcademicYearController` (`com.operion.organisation.api`) — `SchoolClass` creation needs to pick both, and neither had any REST surface. `AcademicYearController` deliberately excludes a mark-current action — a real lifecycle decision with a one-current-at-a-time invariant nothing wired up yet needs.
- `SectionEnrollmentController` (`com.operion.student.api`, `GET /api/v1/sections/{sectionId}/enrollments`) — the Attendance register needs to know who's currently enrolled in a section to build the marking grid, and the only enrollment listing that existed was keyed by `studentId` (`/api/v1/students/{studentId}/enrollments`, a student's own history), not by section. Both Fees (resolving a picked student's current enrollment) and Examinations (composing a school class's full roster across all its sections, since `ExamSchedule` is class-scoped not section-scoped) reuse these two enrollment listings.
- `ExamController.get(examId)` (`GET /api/v1/examinations/exams/{examId}`) — every other top-level entity with a detail page (`GradingScaleController`, `FeeStructureController`, …) already had a GET-by-id; `Exam` didn't, and navigating straight to `/examinations/exams/:examId` needs one (list+find across every academic year, the fallback used elsewhere at this data scale, isn't reasonable when the exam's own academic year is what's unknown up front).
- `AnnouncementController.feed()` gained an optional `status` query param (defaulting to `PUBLISHED`, preserving its prior behavior) — the endpoint was written purely as "the consumer-facing published feed," but an admin composing announcements needs to find their own `DRAFT`s again to publish or cancel them, and the repository already had a status-parameterized finder (`findByStatus`) sitting right there unused for anything but `PUBLISHED`.
- None of the five simple-CRUD controllers among these (`Person`/`Campus`/`AcademicYear`/`SectionEnrollment`/`Exam.get`) have a dedicated service — each entity has no business rules beyond "save the row" or a plain repository read; `Announcement.feed()` and `LeaveRequest.list()` both just reuse branching logic already private to the controller, same reasoning.
- CORS support in `WebConfig` (`addCorsMappings`, origins from `app.cors.allowed-origins`, defaulting to the Vite dev port `http://localhost:5173`) — needed because the plan's frontend direction is direct SPA→API calls with no BFF, so the backend itself must allow the browser origin, not just a dev proxy.
- **Two real bugs, not just gaps, both only surfaced by driving the app from an actual browser origin** (the backend's own `curl`/`@DataJpaTest` testing never exercised either path):
  1. `JwtAuthenticationInterceptor` was rejecting every CORS preflight (`OPTIONS`) request with 401, because preflight requests never carry the real bearer token and the interceptor's `isPublic()` allowlist didn't know about them — silently broke every cross-origin call. Fixed by letting `HttpMethod.OPTIONS` bypass auth unconditionally in `preHandle()`.
  2. `ApiExceptionHandler` had no handler for `DataIntegrityViolationException` — a DB-level unique-constraint violation (e.g. a duplicate `AcademicYear` name or `GradeLevel` sequence within an org) fell through to a raw, unhandled 500 instead of the same clean `{error: string}` JSON shape every other failure mode gets. This affects **every** module with a unique constraint, not just the two touched here. Fixed by mapping it to 409 with a generic message (the real `DataIntegrityViolationException.getMessage()` leaks raw SQL/constraint names, not safe to return to a client).
- **A recurring frontend bug pattern, hit a third time**: `RoutesPanel`'s "Add route" dialog fetched its vehicle picker once at mount, same as `SchoolClassesPanel`'s already-fixed bug — a vehicle added moments earlier in the sibling `VehiclesPanel` on the same page never showed up, since nothing re-fetched after the initial load. Fixed the same way: refetch when the dialog opens. `StudentAssignmentPanel`'s route picker and `RouteDetailPage`'s vehicle picker have the same latent shape (fetch-once-at-mount) but weren't hit by this session's flow, since navigating between `/transport` and `/transport/routes/:id` remounts the page fresh each time. Worth a proactive sweep before this bites a fourth time.

**Resolved**: the `INSERT IGNORE` vs plain `INSERT` inconsistency across the permission-seed migrations (`V2`/`V6`/`V8`/`V10` use `IGNORE`, `V4` and `V12` onward don't) was flagged as an open question for several sessions. Checked directly: every migration inserts only its own module's permission codes, none overlapping any other migration's codes, so `IGNORE` was never load-bearing for either idempotency or collision-avoidance — Flyway migrations don't re-run anyway once applied. No functional difference, nothing to fix, and the already-applied early migrations can't be edited in place regardless (same checksum constraint that required `V23` instead of touching `V5`). Closing this out — it's just stylistic drift from an earlier session, not a bug.

## RBAC / permission enforcement (closed, the former "largest remaining gap")

Built directly on top of the Foundation-era data model (`Role`/`Permission`/`OrganisationMembership`, all previously unused) with three decisions confirmed up front: **hand-rolled `@RequirePermission` + a second `HandlerInterceptor`**, not Spring Security (matches the deliberate earlier call to skip `spring-boot-starter-security`'s filter chain); **org-wide only for v1, no campus-scoping** (`OrganisationMembership.campus` still exists but isn't checked — every controller today is org-scoped only, so this avoids a second authorization dimension nothing currently asks for); **backend only this pass**, frontend RBAC-awareness deferred.

- `com.operion.authorization`: `RequirePermission` (method-level annotation, class-level default; **no annotation = reachable by any authenticated org member** — the deliberate default for cross-cutting lookup/picker endpoints like Campus/AcademicYear/Person/Permission-catalog listings and the `/me`-scoped Communication self-service endpoints, consumed broadly across roles regardless of their specific module permissions), `PermissionInterceptor` (registered in `WebConfig` right after `JwtAuthenticationInterceptor` so `TenantContext` is already populated; resolves the caller's permission codes via a new `OrganisationMembershipRepository.findActivePermissionCodesForUser` JPQL query — union across every ACTIVE membership with an ACTIVE role, since a user can hold multiple roles at once), `AuthorizationDeniedException` → 403 in `ApiExceptionHandler`.
- New management API, since granting anything beyond the auto-provisioned Org Admin was previously impossible: `RoleService`/`RoleController` (create/list/get, `updatePermissions` replace-full-set, `changeStatus` blocking deactivation of the system-default role), `MembershipService`/`OrganisationMembershipController` (`grant` rejecting a duplicate active role, `revoke` blocking the org's last active Org Admin membership), `PermissionController` (read-only catalog listing, ungated), and a minimal `UserController` (create/list/get logins — there was previously no way to create a second user account for anyone besides the org's first admin).
- Permission catalog reconciled via `V24__reconcile_permissions.sql`: dropped the stale Foundation-era `STUDENT_CREATE`/`STUDENT_UPDATE`/`STUDENT_DELETE` (superseded by the Student module's own `STUDENT_MANAGE`), and `DefaultRoles`' Front Desk starter role updated to match. Every other module's already-seeded `*_VIEW`/`*_MANAGE` codes (~50 across all 11 modules) turned out to be a complete, coherent taxonomy that just needed wiring up - reused as-is, one code per controller endpoint, module by module. Cross-cutting Foundation primitives with no dedicated code of their own (Campus/AcademicYear mutations) reuse `ORGANISATION_MANAGE`; class-scoped sub-resources with no code of their own (Section, ClassSubject) reuse the parent's `CLASS_VIEW`/`CLASS_MANAGE`, same pattern for `GradingScaleController` reusing `EXAM_VIEW`.
- **Two real bugs found and fixed while wiring the Role management API, not just gaps**: (1) `Role.permissions` was `@ManyToMany` LAZY by default - `RoleController`'s plain GET endpoints (no `@Transactional`, `open-in-view=false`) would have thrown `LazyInitializationException` serializing it, and passing a controller-loaded `Role` into a separately-transactional service method meant the freshly-resolved target `Permission` set (loaded in a second session) couldn't dedupe against the entity's already-loaded set via plain `HashSet` identity (`Permission` has no overridden `equals`/`hashCode`) - fixed by switching to `FetchType.EAGER` (the catalog is small and bounded, no scale concern) and having `RoleService.updatePermissions`/`changeStatus` take a `Long roleId` and load internally so both resolutions share one persistence context, matching `OrganisationService.changeStatus`'s existing load-by-id-internally precedent over `AcademicService`'s load-in-controller-then-pass-in one. (2) `RoleService.changeStatus`/`MembershipService.revoke` mutated a controller-loaded (detached) entity via a setter but never called `repository.save(...)` again - a no-op against the database, silently. `AcademicService.changeGradeLevelStatus` already established the correct pattern (mutate then explicitly `save()`) but it was missed when these two were first written. Caught by writing tests that re-query the repository independently of the value returned by the service call, not just asserting on the returned in-memory object - worth doing for any future service method with this "controller loads → service mutates" shape.
- Test coverage: `PermissionResolutionTest` (union across multiple ACTIVE memberships, ignores INACTIVE memberships/roles, tenant-isolated for the same user id across two orgs - same convention as every other `*TenantIsolationTest`), `RoleServiceTest`, `MembershipServiceTest`, `PermissionInterceptorTest` (no-annotation passthrough, OPTIONS always bypasses, method-level vs. class-level annotation resolution, deny/allow against real granted permissions). All existing tests across all 11 modules construct services directly rather than going through the web layer, so none were affected by `PermissionInterceptor`'s introduction - confirmed by a full, unchanged-elsewhere green run (104 tests, 0 failures).
- **Fixed in the SaaS/billing + Users-page pass** (was flagged-not-fixed here for a while): `OrganisationController.list()`/`.get()` used to return every organisation in the system to any authenticated caller from any org. Fixed by moving both to the new `PlatformOrganisationController`, reachable only via a platform-admin token (see the SaaS/Billing section below) — the platform-superadmin concept this needed didn't exist until that pass built it. `FEE_DISCOUNT_APPROVE` (seeded, described as "approve fee discounts/scholarships") is still unused - `StudentFeeAssignmentController.assign`/`.revise` bundle discount fields into the same call gated by `FEE_ASSIGNMENT_MANAGE`, and splitting discount-approval into its own finer-grained check would be real service-layer business logic beyond a per-endpoint permission gate. Untouched, still open.
- **Real bug found and fixed later, not part of this pass originally**: `OrganisationMembershipRepository.findActivePermissionCodesForUser`'s `@Query` had a named parameter (`:userId`) with no `@Param` annotation, relying entirely on the `-parameters` javac flag rather than an explicit binding. Since this query backs `PermissionInterceptor` (runs on *every* permission-gated request) and `AuthController.me()`, a backend compiled without that flag — e.g. launched via an IDE's own Java debugger/JDT rather than Gradle, which is exactly what happened mid-session — 500s on nearly the entire app. Fixed with an explicit `@Param`; the same latent gap (present since Inventory's own note above about relying on the flag) was found and hardened the same way in `StockIssueRepository`/`StockAdjustmentRepository`/`StockEntryRepository`/`LeaveRequestRepository`.
- **Another real bug, found while building the Users page**: `UserController.list()`/`.get()` had the identical shape of leak as the `OrganisationController` one above — `User` is deliberately global (one login can span multiple schools, see the Identity model section) so it carries no `organisation_id` to filter on directly, but the endpoints did a raw `userRepository.findAll()`/`findById()` with no tenant boundary at all, so any caller with `MEMBERSHIP_MANAGE` in their own org could see every login's email across *every* organisation on the platform. Fixed by scoping both through `OrganisationMembership` (which *is* `@TenantId`-scoped) - a user is visible only if they hold at least one membership (any status) in the caller's own org. Verified live with two throwaway tenants; `UserVisibilityTest` covers it since this codebase has no `@WebMvcTest`/MockMvc precedent to test the controller directly.
- **Self-lockout guard tightened**: `Role.revoke()`'s existing system-default guard only blocked reducing the role to *zero* permissions - it didn't stop revoking `ROLE_MANAGE`/`MEMBERSHIP_MANAGE` specifically while other permissions remained, which would still permanently lock an org out of ever fixing its own RBAC configuration again through the UI. Tightened to also block revoking either of those two codes from the system-default role specifically, mirroring the equivalent guard `MembershipService.revoke()` already had at the membership level.

**Resolved this session**: making the React admin portal RBAC-aware (nav-level gating + `<Can>`, see the React admin portal section above - per-button gating inside the ten domain modules is still open) and the SaaS/billing layer (Option B, see its own section below) - both previously listed here as undecided.

**Not yet decided**: backfilling Academic Foundation's test gap (the five `changeStatus` methods added in the gap-closure session still have no `@DataJpaTest`-level unit coverage, only incidental Playwright coverage) vs. `FEE_DISCOUNT_APPROVE` above vs. a production build/deploy story for the React admin portal vs. a platform-admin frontend vs. per-button RBAC retrofit across the ten domain modules vs. committing the large pile of currently-uncommitted work (see Current status). ## SaaS/Billing (Option B) — a separate platform-admin plane

The `## SaaS/billing` principle above (`Organisation → Subscription → Plan → Usage → Billing`, kept decoupled from module logic) is now partially built - `Plan`/`Subscription`/`PlatformInvoice` exist, backend-only, no payment gateway.

**The actor-model question that shaped this**: billing/subscription management has two possible actors — the platform owner (you, running Operion as a SaaS business) and a school's own Org Admin (self-service view of their own plan). Two implementation options were on the table: (A) a `PLATFORM_ADMIN` permission bolted onto the existing org-scoped auth model, or (B) a wholly separate, non-organisation-scoped identity plane. **Chose B**, specifically to avoid Option A's risk: any code path that deliberately skips `TenantContext` scoping to go cross-tenant is exactly the shape of bug that caused the `OrganisationController` and `UserController` leaks documented in the RBAC section above — a genuinely separate auth plane keeps the "everything is tenant-scoped by default" invariant airtight on the regular API surface, with cross-tenant access confined to one clearly-separate, clearly-audited place instead.

- `com.operion.platform`: `PlatformAdmin` (a login identity parallel to `User` but extending `BaseEntity` not `TenantScopedEntity` - the same choice `Organisation` itself makes, for the same reason: it must be visible/usable across every org). No self-registration endpoint exists (unlike `Organisation`, which is deliberately public for tenant onboarding) — a platform admin is you, not a customer; bootstrapped instead via a dev-only seed row in `V25__billing_schema.sql` (`admin@operion.platform` / `ChangeMe123!` - **rotate before any real deployment**).
- `com.operion.platform.auth`: `PlatformJwtService` signed with its **own** secret (`app.jwt.platform-secret`, distinct from `app.jwt.secret`) so a leaked org-token secret can never mint a platform token or vice versa - cryptographically separate, not just logically. `PlatformAuthenticationInterceptor` is mounted only on `/api/v1/platform/**`; `WebConfig` explicitly `excludePathPatterns` that prefix from `JwtAuthenticationInterceptor`/`PermissionInterceptor`, so the two auth planes never run on the same request. Reuses `TenantContext`'s actor slot (organisationId left `null`, which `MultiTenancyConfig` resolves to its `NO_TENANT` sentinel) purely for `created_by`/`updated_by` auditing - safe because no entity reachable on this path carries `@TenantId`.
- `com.operion.billing`: `Plan` (catalog, org-independent), `Subscription` (**insert-only per-org history**, same convention as `TeacherAssignment`/`StudentEnrollment` - changing plans ends the old row and inserts a new one, never mutates `planId` in place; one ACTIVE per org enforced in `BillingService`; `pricePerStudentPerYear` snapshotted at subscription time so a later `Plan` price change never retroactively alters an org's agreed rate), `PlatformInvoice` (**usage folded directly in** as a snapshotted `studentCountAtBilling` column rather than a separate `UsageRecord` entity - no proration/mid-cycle-change requirement exists yet to justify the extra table; student count is computed live off `StudentRepository.countByStatus(ACTIVE)` at generation time, scoped to the target org via the tenant-context gotcha workaround noted in the Multi-tenancy section above). `PlatformInvoiceStatus` is just `ISSUED`/`PAID` - `markPaid` is a manual platform-admin action, no payment gateway integration.
- API surface entirely under `/api/v1/platform/` - `PlatformAuthController` (login/me), `PlanController`, `SubscriptionController`, `PlatformInvoiceController`, plus `PlatformOrganisationController` (the relocated `OrganisationController.list()`/`.get()`, closing that cross-tenant gap). None of these use `@RequirePermission` - there is no granular permission system on the platform plane, just "does this token belong to a `PlatformAdmin`."
- Migration `V25__billing_schema.sql`. Test coverage: `PlatformAuthenticationServiceTest` (login/token issuance, wrong-secret rejection - `PlatformJwtService`/`PasswordEncoder` constructed by hand rather than pulling in Spring config the test doesn't need, same reasoning as the `AuditLogService`-avoidance pattern noted in the `@DataJpaTest` gotcha above), `SubscriptionLifecycleTest`, `BillingCrossOrgVisibilityTest` (proves platform-level queries deliberately see across every org, the inverse of every `*TenantIsolationTest` in this codebase).

**Not yet built**: a platform-admin frontend — nothing in `web/` calls `/api/v1/platform/**` yet, matching the RBAC pass's own earlier precedent of shipping backend-only first. Payment gateway integration. A self-service billing view for Org Admins to see their own school's plan/subscription.
